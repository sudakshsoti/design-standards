Tabs are not filters

Tabs and filters both cut a screen down, and that surface similarity is the trap. Tabs switch between a small fixed set of structurally different peer views; filters narrow one dataset into subsets an analyst can combine, save and share. The standing error is a tab bar wearing a column's values — one tab per status, with an "All" tab as the confession.

Our context

Analysts and care managers work dense registries and worklists on large monitors. What decides it: our data is many-valued and multi-dimensional — status, programme, payer, risk tier — and the subsets analysts cut get saved and shared as views. Filters are the default for narrowing; tabs are reserved for views that genuinely differ in structure.

The rule (provisional)

Match the control to what changes.

  • Tabs — a small fixed set of 2–7 mutually exclusive peer views that differ structurally: own layout, columns, actions. One click swaps the screen, and the position is transient.
  • Filters — narrowing one dataset by its columns: many-valued, combinable across dimensions (status AND programme AND payer), saveable as a named view. Same table, fewer rows.

The deciding question: does switching change what the screen is, or only which rows it shows? Structure → tabs. Rows → filters. The tell is that options mirroring a column's values are filter values, and an "All" tab is the confession.

03 / The reasoning

Five forces behind the rule

The rule is not a style preference. Five pressures decide it, and every one of them points the same way for data as multi-valued as ours.

1

Filter values come from the data

A tab set is fixed at design time. Status, programme and payer values grow with configuration, and chrome that mirrors a column cannot keep up.

2

Narrowing is multi-dimensional

Registry questions are conjunctions — status AND programme AND risk tier. Tabs offer one dimension, exclusively.

3

Filter state is an artifact; tab state is position

Analysts save, share and revisit a filter set as a view. Nobody saves which tab they were on. If the selection deserves a name, it is a filter.

4

Tabs promise a structural change

A tab click says the screen will be different. If the same table comes back with fewer rows, the promise is broken.

5

Two systems must not fight

Tabs own structure, filters own rows. A tab switch never silently discards filter state, and a shared filter bar carries only filters that apply to every tab.

04 / Edge cases and anti-patterns

Where to draw the line in review

Most of this rule's work is policing the boundary. A few controls sit close enough to a tab bar to be mistaken for one, and they each resolve cleanly against the deciding question.

Sanctioned

  • One coarse scope strip. At most one, holding 2–3 mutually exclusive populations — "My panel" versus "All members" — placed above the filter bar. A scope switch never silently clears filter state. Anything mirroring a finer column is a filter, not a scope.
  • A saved-view strip is a filter feature, not a tab set. It holds named filter states, grows at runtime, and each entry opens the same table with the same columns. Shopify's IndexFilters does exactly this and still calls them tabs; the behaviour is what governs, not the label.
  • AI filters produce ordinary filter chips — visible, editable and removable like any hand-built filter, and saveable as the same kind of view.
  • A presentation switch is neither a tab set nor a filter, and it must never reset filters. Toggling the same rows between a table and a chart is a view toggle; full guidance is deferred to a future record.

Reject in review

  • A tab per column value — one tab per status, per programme, per payer. That is a filter dimension wearing chrome.
  • An "All" tab. It admits the set was one list the whole time.
  • A "Section" filter spanning structurally different views, forcing one table to serve columns that only fit one of them.
  • A tab switch that silently clears applied filters. Carry the filter state across, or say plainly that it does not apply to this tab.
  • Ordered steps as tabs. Ordered steps are a stepper, not tabs — see stepper orientation, which draws the same boundary from the other side.
05 / What the major design systems say

The boundary is convention, not a house opinion

Every system that documents both controls draws the same line, and one draws it explicitly. Carbon — IBM's system for data-heavy products, closest to ours — names filtering as a reason not to reach for tabs. Links are in the references.

IBM · Carbon — closest to our world

Filtering is listed under "when not to use" tabs

Carbon defines tabs as grouping "different but related content, allowing users to navigate views without leaving the page", then puts filtering in its when-not-to-use list: "When toggling between different formats of the same content or filtering the same content, use content switcher instead." Its separate Filtering pattern carries the other half — filtering "allows a user to add or remove data items from a displayed data set by turning on and off certain predefined attributes", and "multiple filter categories may be applied to the same data set". We take the boundary whole. Where Carbon routes format toggles to a content switcher, our runtime, many-valued narrowing goes to filters, and a switcher is reserved for presentation.

tabs navigate views · filters narrow a dataset
Shopify · Polaris — the complication

Saved filter sets rendered as tabs

Polaris runs against the grain on purpose. IndexFilters lets merchants "filter, search, and sort their index table data and create unique saved views from the results", and those views are tabs: "Each tab represents a subset of the list that has been sorted, filtered, and or queried and saved with a unique name." Read the behaviour, not the label — every one of those tabs opens the same table with the same columns, and the set grows at runtime. That is a saved-view strip wearing tab clothes, which is exactly what we sanction in §04; it is not licence for a tab per column value.

views are named filter states
Nielsen Norman Group

One panel at a time, and the fewer the better

NN/g's definition is exclusivity itself: tabs "allow users to selectively view a single panel of content from among a list of options", suited to content with clear groupings. It rules out the comparison case — tabs fit "when users don't need to simultaneously see information presented under different tabs", otherwise "users must repeatedly switch between tabs to compare or reference information". On count it is blunt: "The fewer tabs, the better." Analysts comparing cohorts across statuses are precisely the users this excludes.

no cross-tab comparison · few tabs
Atlassian

Grouping similar content on one page

Atlassian keeps it to a line: "Tabs are used to organize content by grouping similar information on the same page." Organising content, not subsetting rows — the framing matches everyone else's even without a stated filtering exclusion.

organise content, not rows
Synthesis

The pattern for tools like ours

For a desktop, analyst-facing product over many-valued data, the field points one way: tabs carry a handful of structurally different peer views, filters carry every runtime subset of a dataset, and named views are a filter feature. Polaris is the only system that blurs the line, and it does so by making tabs behave like saved filters, not the reverse.

filters default · tabs for structure
06 / Recommendation for VC

Filters are the default for narrowing

The house rule

  • Filters are the default for registries, worklists, member and cohort tables — anywhere the question is which rows, not which screen. Show applied filters as chips, a result count, and the ability to save the set as a named view.
  • Tabs are reserved for 2–7 structurally different facets of one record: a measure's Definition, Population and Results, each with its own columns, layout and actions.
  • No tab per column value, ever. If the options come from a column, they are filter values; if two tabs would render the same columns, they are one view with a filter.
  • One coarse scope strip is sanctioned — 2–3 mutually exclusive populations, above the filter bar, and it never silently clears filter state.
  • AI filters produce ordinary filter chips, visible and editable like any hand-built filter.
  • Presentation toggles are deferred. Switching the same rows between a table and a chart is neither control, and it must never reset filters.
