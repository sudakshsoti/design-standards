A legend is a key,
not a control

Most charts do not need a legend — label the marks. When marks overlap or interleave, the key sits below the plot on the axis-label tier, colour lives in the swatch and never in the text, and it reads in the same order as the chart. It stays a static key unless hiding a series is real work, and even then it never filters anything.

Our context

Analysts and care managers read dense dashboards on large monitors across several separate analytics apps — dashboards, registries, measure builders. The same reader moves between those apps all day, so a key that changes size, order or behaviour between them stops being a key and becomes something to relearn.

The rule (provisional)

Label the marks first; reach for a legend only when they cannot carry their own names.

  • A legend only for overlapping or interleaved marks — 3+ stacked segments, 2+ lines, a continuous colour ramp. Everything else gets a direct label.
  • Below the plot, left-aligned to its left edge. Never floated right, never a right-hand rail; wraps to a second row before it compresses.
  • Axis-label tier type, colour in the swatch. Same size as the chart's axis labels; the label stays neutral ink, the swatch carries the mark colour.
  • Order follows the chart, never the alphabet — stacking order, line value at the right-hand edge, bar order.
  • Static by default. A key becomes a control only when hiding a series is real analytical work, and then it toggles a series off and on — it never isolates one.
  • Never a filter. Hiding a series changes this one chart's view, nothing else — not another chart, not an export, not a saved view.

The deciding question is: is hiding a series analytical work, or decoration?

01 / Quick reference

Key, direct labels, or nothing

A legend is the last resort, not the default. Most chart situations already carry their own names; the table below sorts which do.

Chart situation What carries the names Why
Single-series chart A title or axis label, not a key. One category — a legend would duplicate it for nothing.
Sorted bar chart Bar-end or axis labels. Each bar already names itself; sort order carries the ranking.
2+ line series A legend below the plot. Lines cross and overlap; only a key ties colour back to name.
3+ stacked segments A legend below the plot. Interleaved fills can't each carry a label without collision.
Sequential or diverging ramp A gradient legend, labelled at its ends. A continuous scale has no discrete members to label directly.
Small multiples A title per tile — no legend. Each tile is already named; a shared key would repeat the titles.
Dashboard tile Nothing — the tile gets a panel instead. No legend at tile scale; a tile that needs a key needs a panel.
Past 6 categorical series Group the tail into "Other", or switch to position. Past 6 categories colour stops separating.
02 / The spec

Size, colour, order, placement

Seven properties are fixed, not a matter of taste. The demos on this page are drawn at reduced schematic scale; the 12px type floor below applies to product charts, not to these illustrations.

Property The rule Why
Placement Below the plot, left-aligned to the plot's left edge, wrapping to a second row rather than compressing. Cap at 2 rows; past that, group the tail. A fixed spot the eye returns to without hunting; a right rail or a floated key competes with the plot for the same scan path.
Type size The axis-label tier — same family and size as the chart's axis labels, sentence case, no uppercase tracking, never below 12px in product. Legend labels are text, so they hold 4.5:1 against the plot background.
Label colour Neutral ink (var(--ink-2)) — colour lives in the swatch, never in the text. Coloured label text duplicates the swatch and loses contrast at small sizes.
Swatch shape Follows the mark: filled square for bar, stack and area fills; a short 2px rule for line series; a labelled gradient bar with end labels for a ramp. A dot or dumbbell mark is out of scope here — see dot plots and ranges. Swatches are graphical objects, so they hold 3:1 against the background.
Order Follows the chart, never the alphabet: stacked segments in stacking order, lines by value at the right-hand edge, bars in bar order. A key whose order contradicts the mark order is a defect.
6-key cap Cap 6 categorical keys. Past 6, group the tail into "Other" or switch to position. Defers to colour for data.
Ramp keys Never clickable. There are no discrete members to toggle.

03 / Clickable or not

Static by default; a control only when hiding is work

A legend is a static key everywhere, with one exception. When an exploratory panel holds 3+ comparable series and hiding one is real analytical work, the key becomes a button row — but the contract is exact: toggle, not isolate; a non-colour hidden state; a reset; no rescale.

One click isolated Diabetes, and colour is the only signal. Every key still reads aria-pressed="true"; a colour-blind reader or a keyboard user gets no indication that Asthma and Depression dropped out. Isolate-on-click and a colour-only hidden state both fail.

Depression is hollow and struck through, not just dimmed; Asthma carries the focus ring; "Show all" resets the row. Each key is a real button, hit area at least 24×24 CSS px, and the axis never moves — the remaining lines look exactly as they did before the click.

04 / One legend everywhere

The same key in every app

Every analytics app renders the legend the same way — placement, type tier, order rule, swatch shapes, states, and whether keys are clickable at all. Per-app legend variants are a defect, not a local decision.

  • A per-app legend position — floated right in one app, below the plot in another.
  • A per-app type size, dropping the key below the axis-label tier in just one surface.
  • An app whose legend click narrows the underlying dataset instead of one chart's view.
  • An app that sorts keys alphabetically while the rest order by the chart.
  • An app showing more than 6 keys with no "Other" grouping.
  • One app toggling a series on click while another isolates it.
05 / The reasoning

Five forces behind the rule

A legend costs the reader a round trip between the key and the plot. Every rule above exists to make that trip as rare, as fast and as consistent as possible.

1

A legend is a round trip

Every glance at the key costs a saccade a direct label would have saved. See colour for data on when colour is the right channel at all.

2

Small type fails first

The key is already the smallest text in the chart, so it gets the axis-label tier — not a size below it.

3

Colour belongs to the mark

Coloured label text loses contrast and repeats what the swatch already said.

4

A control that looks like a label gets clicked by accident

A click that reshapes the data is not recoverable by looking at it.

5

Consistency is the whole value of a key

One grammar across every app means the reader learns it once.

06 / What the major design systems say

Agreement on the key, disagreement on the click

Every source agrees a legend is a last resort; they split on what a click should do. Carbon isolates a series on click, Highcharts toggles it — VC picks toggle, and says so plainly rather than implying the two agree.

IBM Carbon — Legends

Avoid the legend when a direct label will do

Carbon: "When possible, avoid using a legend and label data representations directly. Legends rely on visual association, which can make a chart more difficult to understand." A chart with one category needs no legend at all. Legends sit at the bottom by default. Hovering a category dims the others to 30% opacity, and clicking a legend item isolates that category — the opposite of VC's toggle. Carbon itself marks this legend guidance a work in progress.

direct label first · click isolates
Highcharts — legend.events.itemClick

The default click toggles, it doesn't isolate

Highcharts' own API reference: "The default action is to toggle the visibility of the series, point or data class." This is the behaviour VC's toggle default matches — one series off and on, the rest untouched.

click toggles visibility
Material Design 3 — Data visualization accessibility

Labels and keyboard access, not a size or placement default

Material asks charts to "provide labels for legends, data points, axes, and marks" and requires proper ARIA and keyboard navigation on any interactive chart. It does not specify a type-size floor or a placement default — VC's placement and 12px floor are its own.

labelled and keyboard-accessible
Atlassian — Data visualization colour

Legend text follows text contrast, not graphical contrast

Atlassian assigns the legend the color.text role, caps categorical charts at 5–6 colours, and holds chart colours to 3:1 against surfaces while text needs 4.5:1 — the same split VC draws between swatch and label. It does not rely on colour alone.

text-role legend · 5–6 colour cap
WCAG 2.2

The floors an interactive key must clear

SC 2.5.8 sets a 24×24 CSS px minimum pointer target — the size of every .k.act button. SC 1.4.11 sets 3:1 for the swatch as a graphical object; SC 1.4.3 sets 4.5:1 for the label text. SC 1.4.1 forbids colour as the only signal — the reason the hidden state also carries a hollow swatch and a strikethrough.

24px target · 3:1 swatch · 4.5:1 text
07 / Recommendation for VC

Static key, axis-tier type, one grammar

The house rule

  • Label directly; a legend only for overlapping or interleaved marks. A single series, a sorted bar chart and small multiples never get one.
  • Below the plot, left-aligned, on the axis-label tier. Never floated right, never above the title, never smaller than the axis labels.
  • Colour lives in the swatch; the swatch shape follows the mark. Neutral label text, a square for fills, a rule for lines, a labelled gradient for a ramp.
  • Order follows the chart, capped at 6 categorical keys. Stacking order, right-edge value, or bar order — never the alphabet; group the tail past 6.
  • Static by default; a toggle only when hiding a series is real work. Click toggles one series off and on — it never isolates — and a stacked chart never gets an interactive key.
  • Never a filter, and identical in every app. Hiding a series changes one chart's view only; placement, type, order and behaviour never vary by app.
