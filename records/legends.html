A legend is a key,
not a control

Most charts do not need a legend, so label the marks instead. When marks genuinely overlap, the key goes below the plot at axis-label size, ordered the way the chart is ordered, and never truncated. It never takes a click. A reader who needs fewer series on screen gets small multiples or the filter bar.

Our context

Analysts and care managers read dense dashboards on large monitors, across several separate analytics apps: dashboards, registries, measure builders. The same reader moves between those apps all day, so a key that changes size, order or behaviour between them is one more thing to work out on every screen.

The rule (provisional)

Label the marks first; reach for a legend only when they cannot carry their own names.

  • A legend only when marks overlap or interleave: 3+ stacked segments, 2+ lines, a continuous colour ramp. Everything else gets a direct label.
  • Below the plot, left-aligned to its left edge. Never floated right, never a right-hand rail. It wraps to a second row, then stacks into one column, before it ever compresses a name.
  • Axis-label tier type. The same size as the chart's axis labels, and never a step below it.
  • Order follows the chart, never the alphabet. Stacking order, line value at the right-hand edge, or bar order.
  • Five keys, then group the tail. The 6th key is "Other" on a neutral swatch, never a 6th hue.
  • Never clickable. A key that toggles or isolates a series is a control wearing a label. When a reader needs fewer series on screen, small multiples or the filter bar does that job.
  • It never changes what the chart shows. Narrowing the data belongs to the filter bar and to saved views. See tabs are not filters.

The deciding question is: does the reader have to look away from the plot to know what they are looking at? If not, the chart does not need a key.

01 / Quick reference

Direct labels first, a key only when marks collide

Most chart situations already name themselves. The table sorts which ones do, and which genuinely need a key.

Chart situation What carries the names Why
Single-series chart A title or axis label, not a key. One category, so a legend would duplicate it for nothing.
Sorted bar chart Bar-end or axis labels. Each bar already names itself; sort order carries the ranking.
2+ line series A legend below the plot. Lines cross and overlap; only a key ties colour back to name.
3+ stacked segments A legend below the plot. Interleaved fills can't each carry a label without collision.
Sequential or diverging ramp A gradient legend, labelled at its ends. A continuous scale has no discrete members to label directly.
Small multiples A title per tile, no legend. Each tile is already named; a shared key would repeat the titles.
Dashboard tile Nothing: the tile gets a panel instead. No legend at tile scale; a tile that needs a key needs a panel.
Past 5 categorical series Group the tail into "Other" on a neutral swatch, or switch to position. The categorical set holds five separable hues; a 6th has none left.
02 / The spec

How to draw the key

Eight properties are fixed. The demos on this page are drawn at reduced schematic scale, so the 12px floor and the pixel spacing below apply to product charts rather than to these illustrations.

Property The rule Why
Placement Below the plot, left-aligned to the plot's left edge, not the card's padding box. 12px between the plot's lowest label row and the first key, 16px between keys, 6px between wrapped rows, 4px between a swatch and its label. No border, no fill, no card of its own. The plot's left edge is where the title and the axis labels already start, so the key joins a line the eye is using instead of adding one. A floated key moves every time the card resizes, so its position is never learnable, and a right-hand rail spends plot width, which is the scarce resource on a dense dashboard.
Type size The axis-label tier: same family and size as the chart's axis labels, sentence case, no uppercase tracking, never below 12px in product. Legend labels are text, so they hold 4.5:1 against the plot background.
Swatch shape Follows the mark: filled square for bar, stack and area fills; a short 2px rule for line series; a labelled gradient bar with end labels for a ramp. A dot or dumbbell mark is out of scope here, see dot plots and ranges. Swatches are graphical objects, so they hold 3:1 against the background.
Order Follows the chart, never the alphabet: stacked segments in stacking order, lines by value at the right-hand edge, bars in bar order. A key whose order contradicts the mark order is a defect.
5-key cap Cap 5 categorical keys. Past 5, group the tail into "Other" on a neutral swatch, or switch to position. Defers to colour for data: the categorical set holds five separable hues, so a 6th key would have to reuse one.
Ramp keys Labelled at both ends, low value first, and never clickable. The reader scans low to high the same way the axis does, so end labels have to match that order.
Long labels Never truncate a key. Wrap to a second row, then stack the key into one column below the plot. A name that still does not fit means the chart has too many series. Series names come from the data and are often long. Two names that share a prefix become the same word once they are cut, and a key that lies about the name is worse than a taller card.
Filtered categories A category the global filters remove takes its key with it. The hue stays pinned to the category, never to its position in the list. A key for a series that is not drawn is a false claim, and a hue that shifts when a filter changes destroys recognition across every chart on the dashboard.

03 / Long names and filtered series

The key never truncates, and never outlives its series

Two things the spec has to survive: names longer than the chart is wide, and a global filter that removes a category underneath it. Neither is an edge case in VC; measure and contract names run long, and every dashboard opens with filters already applied.

Avoid
Members by plan · truncated key
Medicare Advantage HMO Medicare Advantage PPO Commercial Fully Insured

Two keys now read the same. "Medicare Advantage HMO" and "Medicare Advantage PPO" both cut to "Medicare Advan…", so the key can no longer say which line is which. Nothing about the chart is wrong; the key threw the answer away to save a row.

Use
Members by plan
Medicare Advantage HMO Medicare Advantage PPO Commercial Fully Insured

Stacked into one column, every name survives. The key wraps to a second row first; when names run this long it stacks, and the card grows by two rows instead of losing the difference between two plans.

Avoid
Members by contract type · Medicaid filtered out
Commercial Medicare Medicaid

The filter took Medicaid out, and the two survivors changed colour. Commercial was blue on every other chart in the dashboard and is vermilion here, because the hues were handed out by position instead of pinned to the category. The Medicaid key is still sitting there naming a series that is not drawn.

Use
Members by contract type
Commercial Medicare

Medicaid's key left with its mark, and Commercial is still blue. The hue belongs to the category, so the reader recognises it across every chart; the key names exactly what the plot draws and nothing else.

04 / The interactivity rule

The key never takes a click

No legend in VC is clickable. Not to toggle a series off, not to isolate one. The two demos below show what breaks when a key becomes a control, and what to reach for when a chart really does carry too many series to read.

Avoid
Members by contract type · one segment hidden
Commercial Medicare Medicaid

Hiding Medicaid changed the total, so the axis rescaled. The two remaining segments now fill the frame. The bars look the same height as before but no longer mean the same thing, which is why a stacked total must never be something a reader can switch off.

Use
Members by contract type
Commercial Medicare Medicaid

A plain static key, and the totals stay honest. Nothing here is clickable, so the column always adds up to what it claims.

Avoid
Condition rates · isolated on click
Asthma Depression Diabetes

One click isolated Diabetes, and colour is the only signal. Every key still reads aria-pressed="true", so a colour-blind reader or a keyboard user gets no indication that Asthma and Depression dropped out. Making this correct needs a real button, a 24px target, a non-colour hidden state and a reset control, which is four more things to get wrong.

05 / One legend everywhere

The same key in every app

Every analytics app renders the legend the same way: placement, type tier, order rule, swatch shapes, states, and whether keys are clickable at all. Per-app legend variants are a defect, not a local decision.

The same key three times. Below the plot, left-aligned, axis-label size, ordered like the chart, static in all three. What the analyst learns on the dashboard still holds in the registry.

  • A per-app legend position, floated right in one app and below the plot in another.
  • A per-app type size that drops the key below the axis-label tier on one surface.
  • A legend key that takes a click at all, whether it toggles, isolates or dims.
  • A key sorted alphabetically while the rest of the product orders by the chart.
  • More than 5 keys with no grouped tail.
  • A key truncated to fit the row instead of wrapping or stacking.
  • A hue reassigned by position, so a category changes colour when a filter changes.
06 / The reasoning

Five reasons the rule holds

Every rule above comes back to one cost: a legend makes the reader look away from the plot to find out what they are looking at. The rules keep that trip rare, and identical everywhere.

1

Label the mark before you add a key

Every glance at a key is a trip away from the plot. A direct label answers the same question without moving the reader's eye. See colour for data on when colour should carry a category at all.

2

Hold the axis-label size

The key is already the smallest text in a chart, so it takes the axis tier and never a step below it.

3

Never truncate a name

Series names come from the data, and two that share a prefix become the same word once they are cut.

4

Never make a label take a click

A control that looks like a label gets clicked by accident, and the state it leaves behind is invisible to a reader who looked away.

5

Draw the same key in every app

One grammar across the product means an analyst learns the key once instead of on every screen, and a hue pinned to its category survives every filter.

07 / What the major design systems say

Agreed on the key, alone on the click

Every source agrees a legend is a last resort, and both systems that specify click behaviour make the key interactive. Carbon isolates a series on click, Highcharts toggles it. VC allows neither, and this record says so rather than implying the field backs us.

IBM Carbon — Legends

Avoid the legend when a direct label will do

Carbon: "When possible, avoid using a legend and label data representations directly. Legends rely on visual association, which can make a chart more difficult to understand." A chart with one category needs no legend at all. Legends sit at the bottom by default. Hovering a category dims the others to 30% opacity, and clicking a legend item isolates that category. VC allows neither that nor a toggle. Carbon itself marks this legend guidance a work in progress.

direct label first · click isolates
Highcharts — legend.events.itemClick

The default click toggles, it doesn't isolate

Highcharts' own API reference: "The default action is to toggle the visibility of the series, point or data class." A VC chart built on Highcharts has to switch that default off, which is a cost we take deliberately for one predictable key.

click toggles visibility
Material Design 3 — Data visualization accessibility

Labels and keyboard access, not a size or placement default

Material asks charts to "provide labels for legends, data points, axes, and marks" and requires proper ARIA and keyboard navigation on any interactive chart. It does not specify a type-size floor or a placement default: VC's placement and 12px floor are its own. A static key sidesteps the requirement, because there is nothing to operate.

labelled and keyboard-accessible
Atlassian — Data visualization colour

Legend text follows text contrast, not graphical contrast

Atlassian assigns the legend the color.text role, caps categorical charts at 5–6 colours, and holds chart colours to 3:1 against surfaces while text needs 4.5:1. VC takes the bottom of that range: five hues, with the tail grouped into a neutral "Other".

text-role legend · 5–6 colour cap
WCAG 2.2

The floors we keep, and the ones we avoid

SC 1.4.11 sets 3:1 for the swatch as a graphical object and SC 1.4.3 sets 4.5:1 for the label text. Both bind our static key. SC 2.5.8's 24×24 px target and SC 1.4.1's ban on colour as the only signal are what a clickable key would add, which is part of why we do not build one. The label text carries no colour requirement of its own, so 4.5:1 is the binding check on whatever colour it renders in.

3:1 swatch · 4.5:1 text
08 / Recommendation for VC

A static key, drawn the same way everywhere

The house rule

  • Label directly. A legend only when marks overlap or interleave. A single series, a sorted bar chart and small multiples never get one.
  • Below the plot, left-aligned, at axis-label size. Never floated right, never above the title, never smaller than the axis labels.
  • The swatch shape follows the mark. A square for fills, a rule for lines, a gradient labelled at both ends for a ramp.
  • Order follows the chart, capped at 5 categorical keys. Stacking order, right-edge value or bar order, never the alphabet. Group the tail into a neutral "Other" past 5.
  • Never truncate a key. Wrap, then stack into one column; a name that still does not fit means too many series.
  • A filtered-out category takes its key with it, and hues stay pinned to categories.
  • Never clickable. A reader who needs fewer series gets small multiples; a reader who needs fewer rows gets the filter bar.
  • Identical in every app. Placement, type, order and behaviour never vary by surface.
